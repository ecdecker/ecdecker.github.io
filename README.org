#+TITLE: Managing Emily's website
#+SUBTITLE: A practical guide to writing, updating, and publishing the site
#+OPTIONS: toc:2 num:nil

You can manage the day-to-day content of this website with Pages CMS, GitHub's
file editor, or a local checkout. They all edit the same files in Git, so Pages
CMS is a convenience rather than a required or separate publishing system. You
do not need to edit the design or understand how the site is built.

Some tasks are not day-to-day writing at all: claiming your author profiles,
filling in your social and scholarly links, taking the repository over, and
pointing the domain at it. Those are one-time steps only you can do, and they
are collected in [[file:docs/SITE-OWNER.md][Steps for the site owner]].

The important folders are:

- =content/posts/= — articles
- =content/_index.md= — the English home page
- =content/_index.fr.md= — the French home page
- =content/_index.mg.md= — the Malagasy home page

Avoid changing =themes/=, =layouts/=, =config/=, =tools/=, =data/=,
=resources/=, or =public/=. Those folders run the site rather than hold its
everyday content.

* How publishing works

Each saved change in GitHub is called a /commit/. An approved pull request
merged into the protected =main= branch automatically rebuilds and publishes the website. This normally takes
a few minutes.

To see whether publishing succeeded, open the repository's *Actions* tab in
GitHub. A green check means the site published successfully. A red cross means
the change needs attention; see [[#common-problems][Common problems]].

GitHub keeps the history of every commit, so an earlier version can be
recovered if necessary.

* Choose an editor

For ordinary notes, open =/admin/= on the website or go directly to
[[https://app.pagescms.org/][Pages CMS]], sign in with an authorized GitHub account, and choose this
repository. The visual editor includes a *Source* mode for Markdown that needs
to remain exact. New notes start as drafts, and Pages CMS cannot rename or
delete published notes.

GitHub's file editor and a local checkout remain fully supported. Use them for
translations, article-local files, Hugo shortcodes, unusual front matter, or
anything else the CMS form does not expose. Pages CMS preserves front-matter
keys outside its form rather than deleting them.

Box and Zotero synchronization is a separate input workflow. Imported Box
snapshots and generated Zotero bibliographies are intentionally not editable
in Pages CMS. Do not author one article independently in both Box and Pages
CMS; choose one authority for that article. The technical ownership and trial
instructions are in [[file:docs/AUTHORING.md][the authoring note]].

* Edit an existing article

1. In GitHub, open =content/posts/=.
2. Open the article's =.md= file. Some articles are folders; for those, open
   the folder and then open =index.md=.
3. Select the pencil icon, *Edit this file*.
4. Make the change. Leave the information between the two =---= lines at the
   top intact unless you intend to change it.
5. Select *Commit changes*.
6. Enter a short description, such as “Correct opening paragraph.”
7. Commit to a new branch and open a pull request into =main=.
8. Wait for the publishing action to finish, then check the live page.

* Create a new article

Use a folder for every new article. This keeps its writing, images, and
downloads together.

** 1. Choose its name

Choose a short name made of lowercase words separated by hyphens. This name
becomes part of the page's web address.

Good: =garden-field-notes=

Avoid: =Garden Field Notes=, =garden_field_notes=, or a name containing a
date. Do not rename the folder after the article has been published, because
that would change its web address.

** 2. Create the article file

1. In GitHub, select *Add file*, then *Create new file*.
2. In the filename box, enter:

   #+begin_example
   content/posts/garden-field-notes/index.md
   #+end_example

   Replace =garden-field-notes= with your chosen name.
3. Paste this starting point:

   #+begin_src markdown
   ---
   title: "Garden field notes"
   description: "A one- or two-sentence summary of the article."
   date: 2026-08-27
   draft: true
   tags: ["field notes"]
   locations: []
   ---

   Write the opening paragraph here.

   ## First section

   Continue the article here.
   #+end_src

4. Change the title, summary, date, tags, and article text.
5. Commit the new file.

The =draft: true= line keeps the article off the public site while you prepare
it. Remove that line when you are ready to publish.

** 3. Understand the information at the top

The lines between =---= and =---= control how the article appears:

| Line          | What to enter                                                     |
|---------------+-------------------------------------------------------------------|
| =title=       | The article title                                                   |
| =description= | A short summary used on article lists and by search engines         |
| =date=        | The publication date in =YYYY-MM-DD= form                            |
| =draft=       | =true= while unpublished; remove the entire line to publish          |
| =tags=        | Optional subjects, such as =tags: ["field notes", "research"]=      |
| =locations=   | Optional places that put the note on the homepage research map       |

Keep the quotation marks around titles and descriptions. Do not add a =#=
heading for the title in the article itself; the site adds the title for you.
Start sections with =##=.

To put a note on the research map, add one or more place names with decimal
coordinates. Use negative latitude south of the equator and negative longitude
west of Greenwich:

#+begin_src yaml
locations:
  - name: "Saint Paul, Minnesota, United States"
    latitude: 44.9537
    longitude: -93.09
#+end_src

The map appears automatically when =locations= is present. No map tag is
needed. Leave =locations: []= when a note is not tied to a place.

* Add images

Commit the original image directly to the article's folder. Do not resize or
compress it first; the site automatically creates smaller AVIF and WebP files
for different screen sizes when it publishes.

Use a clean JPEG or PNG that is at least 1,200 pixels wide when possible. Do
not use SVG files for article images. Give files simple lowercase names with
hyphens, such as =garden-tools.jpg=.

** Upload an image in GitHub

1. Open the article's folder, for example
   =content/posts/garden-field-notes/=.
2. Select *Add file*, then *Upload files*.
3. Choose the original JPEG or PNG.
4. Commit the upload.
5. Edit =index.md= and place the image where it should appear:

   #+begin_src markdown
   ![A wooden table holding three garden tools](garden-tools.jpg "Tools used during the survey")
   #+end_src

The words inside =[]= describe the image for people who cannot see it. Write
a useful, specific description. The quoted text is the visible caption and is
optional.

Filenames are case-sensitive. =garden-tools.jpg= and =Garden-Tools.JPG= are
different names, so the name in the article must match the uploaded file
exactly.

Images used by several pages may instead be stored in =assets/images/=, but
keeping an article's images in its own folder is the simplest approach.

* Add a PDF, spreadsheet, or other download

1. Upload the file to the same folder as the article.
2. Link to the exact filename from =index.md=:

   #+begin_src markdown
   [Download the survey results](survey-results.csv)
   [Read the full report](field-report.pdf)
   #+end_src

A file must be linked from the article or it will not appear on the published
site. The site automatically shows the file type and size beside the link.

* Write and format text

Use these common patterns in an article:

#+begin_src markdown
## Section heading

Write paragraphs with a blank line between them.

**Bold text** and *italic text*

- A bullet point
- Another bullet point

1. A numbered item
2. Another numbered item

[Link text](https://example.com/)

> A quotation
#+end_src

For a source or note, place a marker in the text and its full details at the
bottom of the file:

#+begin_src markdown
This statement needs a source.[^survey]

[^survey]: Community survey, May 2026.
#+end_src

The site collects these notes under a *Sources* heading automatically.

Do not paste HTML, JavaScript, or styling code into an article. Use the
patterns above so the page remains consistent and readable.

* Publish an article

Before publishing, check that:

- the title, summary, and date are correct;
- headings begin with =##=;
- every image has an accurate description inside =[]=;
- image and download filenames match their links exactly;
- every PDF, spreadsheet, or other download is linked from the article; and
- the article is ready to be public.

Then edit =index.md=, remove this line, and commit the change:

#+begin_src yaml
draft: true
#+end_src

The website will publish automatically. Check the *Actions* tab for a green
check, then open the live article.

* Correct, hide, or remove an article

To correct an article, edit its =index.md= file and commit the change. The
published page will update automatically.

To hide an article without deleting it, add this line between the =---= lines
at the top and commit:

#+begin_src yaml
draft: true
#+end_src

Hiding is safer than deleting because the writing and its files remain in the
repository. Permanently deleting or renaming a published article can break old
links. Only do that when you are sure it is necessary.

* Translate an article

English is the default language. French uses =fr= and Malagasy uses =mg=.
Translations are optional; an English article can be published on its own.

For an article stored at:

#+begin_example
content/posts/garden-field-notes/index.md
#+end_example

place translations in the same folder:

#+begin_example
content/posts/garden-field-notes/index.fr.md
content/posts/garden-field-notes/index.mg.md
#+end_example

Copy the original file, translate its =title=, =description=, and article
text, and keep its =date= and =tags= consistent. The site will connect the
language versions automatically. All versions in the folder can use the same
images and downloads.

* Edit the home page

The three home-page files are:

- English: =content/_index.md=
- French: =content/_index.fr.md=
- Malagasy: =content/_index.mg.md=

Edit only the visible wording. Keep lines containing ={{< ... >}}= exactly as
they are; those markers arrange the home page. If you change the meaning of
home-page text, make the equivalent change in all three languages.

* How the site stays fast

The publishing system turns the source material you commit into a lightweight
site automatically:

- Each image is resized for phones, tablets, and larger screens. Browsers
  receive the smallest useful AVIF or WebP version instead of the large source
  file.
- Image compression is chosen to preserve visible detail without spending
  unnecessary data. The original PNG or JPEG is kept in GitHub for future
  editing but is not published to readers.
- The first image is loaded promptly. Later images wait until the reader nears
  them, and image-heavy articles can keep extra images closed until requested.
- The complete page styling travels with the page, so readable content does
  not wait for a separate stylesheet.
- Body text uses fonts already on the reader's device. The decorative heading
  font is small and optional, so a slow connection never blocks the article.
- Downloads show their file type and size before a reader chooses to fetch
  them.
- The published site contains no advertising, analytics, tracking, or
  JavaScript and is made of simple static files that are quick to load and
  straightforward to archive.

You only need to provide clean source files and accurate links. These
optimizations are part of the normal publishing process.

* Preview on your computer (optional)

GitHub publishes each non-draft commit automatically, so working entirely in
GitHub is fine. A local preview is useful when you want to see a draft exactly
as it will appear before publishing it.

Install the current long-term-support version of Node.js. Then open a terminal
in this repository and run this once:

#+begin_src sh
npm install
#+end_src

After that, start the preview with:

#+begin_src sh
npm run site -- start
#+end_src

Then open =http://localhost:1313/= in a browser. Draft articles are included
in this preview. Press =Ctrl+C= in the terminal when finished.

The project provides the rest of its setup and maintenance commands through
the same interface. To see what is available, run:

#+begin_src sh
npm run site -- help
#+end_src

* Common problems
:PROPERTIES:
:CUSTOM_ID: common-problems
:END:

** The article does not appear

- Check whether =draft: true= is still present.
- Confirm that the file is named =index.md= and is inside
  =content/posts/article-name/=.
- Open GitHub's *Actions* tab and wait for publishing to finish.
- Check that the publication date is written as =YYYY-MM-DD=.

** An image does not appear

- Confirm that the image is in the same folder as =index.md=.
- Confirm that the filename in =![]()= matches the uploaded file exactly,
  including capital letters and the extension.
- Use JPEG or PNG, not SVG.

** A download does not appear

- Confirm that the file is in the same folder as =index.md=.
- Add a link to it in the article, such as =[Download](report.pdf)=.

** GitHub Actions shows a red cross

Open the failed action and read the first red error message. The most common
causes are a missing file, a misspelled filename, an SVG image, or damaged
=---= lines at the top of an article. Correct the file and commit again; the
site will retry automatically.

If the cause is unclear, restore the last known-good text from the file's
*History* view, or add =draft: true= while you investigate.

* Quick reference

For a normal new article:

1. Create =content/posts/article-name/index.md=.
2. Start it with title, description, date, and =draft: true=.
3. Write the article using Markdown.
4. Upload original JPEG or PNG images to the same folder.
5. Add image and download links to =index.md=.
6. Commit the work.
7. Remove =draft: true= when ready.
8. Check GitHub Actions, then check the live site.
